## 5. 库存管理（第九章）— 系统核心

### 5.1 库存表关键字段

```
sto_stock
├── sku_id          (FK pro_sku)
├── warehouse_id    (FK sto_warehouse)
├── location_id     (FK sto_location, 可空)
├── quantity        (实际库存)
├── locked_quantity (锁定数量 = 订单未支付/未发货 占用的)
├── batch_no        (批次)
└── UNIQUE(sku_id, warehouse_id, location_id)
```

**可用库存 = quantity − locked_quantity**

### 5.2 场景：仓库与库位初始化

```
管理员 → POST /api/warehouse {warehouseCode, warehouseName, type}
       → WarehouseService.insert

管理员 → POST /api/location {warehouseId, parentId, locationType:1|2|3, locationName}
       → LocationService.insert（可建库区/货架/库位的层级）

Client → GET /api/location/tree?warehouseId=1
       → LocationService.buildTree()
       └─ 返回 {areaId, areaName, shelves:[{shelfId, positions:[{positionId, skuId, quantity}]}]}
```

**实现要点**：四级仓位（仓库→库区→货架→库位）用 `parent_id` 自引用即可。

### 5.3 场景：实时库存查询

```
Client → GET /api/stock/query?skuId=&warehouseId=&keyword=
       → StockController → StockService
       │
       ├─ ① 主查询：SELECT s.*, p.product_name, sku.spec_values, sku.barcode
       │            FROM sto_stock s
       │            JOIN pro_sku sku ON s.sku_id=sku.id
       │            JOIN pro_product p ON sku.product_id=p.id
       │            WHERE (s.sku_id=? OR s.warehouse_id=? OR p.product_name LIKE ?)
       │              AND s.deleted=0
       ├─ ② 按 sku_id 聚合：totalStock, availableStock=quantity-locked_quantity
       ├─ ③ 按 sku_id + warehouse_id 子聚合 → warehouses[]
       ├─ ④ 关联 sto_stock_log 拿 lastInboundTime / lastOutboundTime
       │     (SELECT MAX(operate_time) WHERE sku_id=? AND type=1)
       └─ ⑤ PaginationInnerInterceptor 分页
```

**性能要点**：
- `UNIQUE(sku_id, warehouse_id, location_id)` 已经给了 (sku_id, warehouse_id) 前缀索引，聚合很快
- `lastInboundTime` 子查询会拖慢，建议在 `pro_sku` 上冗余字段或定时刷新

### 5.4 场景：库存流水查询（追溯）

```
Client → GET /api/stock/log/list?skuId=&type=&startDate=&endDate=
       → StockLogService
       └─ 简单分页查询 sto_stock_log
            可视化展示：before_qty → quantity_change → after_qty
```

### 5.5 场景：库存预警

```
Client → GET /api/stock/alert/list
       → StockAlertService
       │
       ├─ ① 低库存预警：
       │    SELECT s.sku_id, sum(s.quantity) AS cur
       │    FROM sto_stock s GROUP BY s.sku_id
       │    HAVING sum(s.quantity) < (SELECT config_value FROM sys_config WHERE key='sys.stock.alert.low.threshold')
       │
       └─ ② 超储预警：
            HAVING sum(s.quantity) > sys.stock.alert.high.threshold
```

**实现要点**：阈值放 `sys_config`，从 Redis 缓存读，配置变更时刷新缓存。

### 5.6 场景：库存盘点

```
① 创建盘点单
Client → POST /api/stock/check {warehouseId, type:1全盘|2抽盘, checkItems?[]}
       → StockCheckService
       └─ INSERT sto_stock_check（type=1 时不传 checkItems，全量快照当前数量）

② 录入实际盘点结果
Client → PUT /api/stock/check/{id}/submit {results:[{skuId, actualQty, diffQty, reason}]}
       → StockCheckService
       │
       ├─ ① @Transactional
       │    ├─ 遍历 results：
       │    │    ├─ 找到对应 sto_stock 记录
       │    │    ├─ 若 diffQty ≠ 0：
       │    │    │    UPDATE sto_stock SET quantity = actualQty WHERE id=?
       │    │    │    INSERT sto_stock_log（type=3 盘点调整, quantity_change=diffQty）
       │    │    └─ 标记盘点项已处理
       │    ├─ UPDATE sto_stock_check SET status=已完成
       │    └─ 提交
       └─ ② 返回
```

**并发要点**：盘点和实时出入库会冲突。建议：
- 抽盘：锁定该 SKU 行（`SELECT FOR UPDATE`）
- 全盘：业务停摆或走"差异暂存"模式（实际数量不入账，先记账差异，确认后入账）

### 5.7 场景：库存调拨

```
Client → POST /api/stock/transfer {fromWarehouseId, toWarehouseId, items:[{skuId, quantity, fromLocationId, toLocationId}], remark}
       → StockTransferService
       │
       ├─ ① 校验 fromWarehouseId ≠ toWarehouseId
       ├─ ② 校验 fromLocationId 下的 quantity ≥ quantity（SELECT FOR UPDATE）
       ├─ ③ @Transactional
       │    ├─ UPDATE sto_stock SET quantity = quantity - ? WHERE id=fromRowId
       │    ├─ INSERT/UPDATE sto_stock SET quantity = quantity + ? WHERE sku_id=? AND warehouse_id=toWarehouse AND location_id=toLocation
       │    ├─ INSERT sto_stock_log (type=4 调拨, source_no=transferNo)
       │    │    两条流水：from 负、to 正
       │    └─ 提交
       └─ ④ 返回
```

**异常分支**：源库位不足 → `50001`；目标库位不存在 → `400`。
