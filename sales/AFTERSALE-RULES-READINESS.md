## 3. 规则一：换货完成接口

### 3.1 已确认

```text
PUT /api/v1/web/aftersale/{aftersaleId}/exchange/complete
```

- 请求需要物流单号。
- 接口属于商家侧售后流程。
- 当前 `type=3` 审核通过后不生成 Refund，这一隔离必须保留，不能复用退款完成事件。

### 3.2 正式文档仍需给出的内容

- 请求字段名是否固定为 `logisticsNo`，长度和字符约束是什么。
- 是否还需要物流公司。
- 调用角色是否固定为 `seller/admin`。
- “complete”表示商家发出换货、客户收到换货，还是整条换货流程结束。
- `ord_aftersale` 需要增加哪些状态；当前只有
  `PENDING(0)/APPROVED(1)/REJECTED(2)`。
- 重复完成、非换货类型、非 APPROVED 状态分别使用什么错误码。
- 是否产生新订单、库存扣减或新的 Outbox 事件；事件名和 payload 尚未冻结。

### 3.3 文件级改造地图

| 层 | 预计文件 | 改造内容 |
|---|---|---|
| Controller | `controller/AftersaleController.java` | 新增固定路径、角色与 `Idempotency-Key` |
| DTO | 新增 `dto/AftersaleExchangeCompleteRequest.java` | 物流单号及正式稿要求的其他字段校验 |
| Service | `service/AftersaleService.java` | 锁行、类型/归属/状态条件更新、幂等与首次响应 |
| VO | `vo/AftersaleResponse.java` | 仅在正式响应要求时增加物流和完成时间 |
| SQL | `sql/V001__customer_address_refund.sql` | 增量列、状态 CHECK、必要索引；不得替换团队 Schema |
| 测试 | Aftersale Service、DTO、HTTP、迁移测试 | 角色、状态、物流必填、重复提交、并发条件更新 |

### 3.4 最低验收矩阵

- `seller/admin + type=3 + 合法状态 + 物流单号`：成功并返回更新后状态。
- 普通用户：`403`。
- 非换货类型：按正式错误码拒绝，数据库不变。
- 不存在：`404`；并发状态已改变：按正式状态错误码拒绝。
- 缺少或超长物流单号：`400`。
- 相同 key、相同载荷：重放首次响应且只更新一次。
- 相同 key、不同物流单号：`50015`。
- 不生成 Refund，不误发 `sales.refund.completed`。

## 4. 规则二：确认收货起两周

### 4.1 已确认

- 起算字段为订单 `receive_time`。
- 时长为两周，即 14 天。
- 超出窗口使用正式 v1.2 已存在的 `50017`。

### 4.2 正式文档仍需给出的内容

- `receive_time + 14 days` 的临界时刻是否仍允许申请。
- 已发货但尚未确认收货的订单是否允许仅退款；当前 v1.2 允许订单状态 `2/3`。
- 窗口适用于 `type=1/2/3` 全部售后，还是只适用于退款、退货。
- 当前 Schema 使用无偏移 `TIMESTAMP`，如何与正式 v1.2 的 UTC 存储/展示约定统一。

### 4.3 文件级改造地图

| 层 | 预计文件 | 改造内容 |
|---|---|---|
| Service | `service/AftersaleService.java` | 归属查询带出 `receive_time`，按正式 UTC 规则校验 14 天 |
| 错误码 | 复用 `ApiErrorCode.REFUND_TIME_WINDOW_EXCEEDED` | 不新造重复错误码 |
| SQL | 通常不需新增字段 | 只有查询计划证明必要时才增加索引 |
| 测试 | Aftersale Service、HTTP | 14 天内、临界点、超期、NULL、时区边界 |

### 4.4 最低验收矩阵

- `receive_time + 14 days` 之前：允许。
- 临界时刻：按正式文档冻结的包含/不包含规则断言。
- 临界时刻之后：`50017`，不创建 `ord_aftersale` 和幂等成功记录。
- `receive_time=null`：处理方式必须由正式同步稿明确，不自行代入 `ship_time/create_time`。
- 同一瞬间使用不同 ISO-8601 偏移表示时，换算到 UTC 后结果一致。

## 5. 规则三：优惠订单部分退款上限

### 5.1 已确认

```text
退款金额上限 =
min(订单项原单价快照 × 本次退款数量 × 50%, 订单项实际支付金额)
```

累计待审核、已通过和已完成金额仍要共同占用可退额度，订单项查询继续加锁，不能因为
增加 50% 上限而丢掉现有并发保护。

### 5.2 当前硬阻塞

`ord_order_item` 目前只有：

```text
price, quantity, subtotal
```

订单头只有整单 `discount_amount/pay_amount`，没有订单项实际支付金额或冻结的优惠分摊
结果。Refund 不能用 `subtotal` 冒充实付，也不能自行按比例猜分整单优惠。

订单模块需先提供下列二者之一：

1. 冻结的订单项实际支付字段及历史数据回填方案；或
2. 正式、可复现、含舍入尾差归属的整单优惠分摊算法。

字段名、精度和回填规则由订单模块/正式 Schema 冻结，本模块不预先命名。

### 5.3 文件级改造地图

| 层 | 预计文件 | 改造内容 |
|---|---|---|
| Schema | 订单模块迁移 + Sales V001 兼容检查 | 订单项实付字段、非负和上限约束、历史回填 |
| Service | `service/AftersaleService.java` | 锁行读取 `price/实际支付`，计算两种上限的较小值 |
| VO | 仅在正式接口要求时调整 | 不主动暴露内部优惠分摊 |
| 测试 | Service、HTTP、迁移测试 | 两个上限分支、累计占用、并发、舍入和历史数据 |

### 5.4 最低验收矩阵

- 50% 计算值小于实付：按 50% 限制。
- 实付小于 50% 计算值：按实付限制。
- 多次申请累计不超过同一上限。
- 两个并发申请只能有一个使累计值达到上限。
- 两位小数和舍入尾差按订单模块冻结规则处理。
- 超额统一返回 `50016`，不得出现部分写入。

## 6. 规则四：`restock` 只允许 `false`

### 6.1 已确认

- Refund complete 请求保留 `restock` 字段。
- 只允许传 `false`。
- 退回商品不进入库存；IVP 不增加可售数量。

### 6.2 与当前正式契约的冲突

当前 v1.2 明确允许：

```text
type=2 + restock=true
```

并要求发送 `refund.completed(restock=true)` 由 IVP 回补库存；当前 SQL 也只约束
`restock=true` 必须属于 `type=2`。因此正式文档同步前不得先改 Service 或 CHECK。

### 6.3 文件级改造地图

| 层 | 预计文件 | 改造内容 |
|---|---|---|
| DTO | `dto/RefundCompleteRequest.java` | 保留非空布尔字段；具体校验方式以统一异常格式为准 |
| Service | `service/RefundService.java` | 在状态更新和 Outbox 前拒绝 `true` |
| SQL | `sql/V001__customer_address_refund.sql` | 将回补类型 CHECK 改为所有记录必须 `restock=false` |
| Outbox | `service/RefundService.java` | 事件仍携带 `restock=false`，不调用任何库存回补路径 |
| VO | Refund 响应 | 字段保留并返回 `false` |
| 测试 | Refund Service、HTTP、迁移测试 | `true` 原子失败；`false` 完成且库存不变；幂等重放 |

### 6.4 正式文档仍需给出的内容

- `restock=true` 使用 `400` 还是状态错误码；本清单不预设。
- 是否所有历史 `restock=true` 先回填为 `false`，还是迁移检测到历史值就停止。
- IVP 对 `refund.completed(restock=false)` 是只记幂等流水还是完全忽略。

### 6.5 最低验收矩阵

- 任意退款类型传 `true`：在退款状态更新和 Outbox 写入前失败。
- 失败后退款仍为 APPROVED，无 `REFUND_COMPLETED` Outbox。
- 传 `false`：退款完成，事件 payload 固定为 `false`。
- 相同 key 重放：只存在一笔完成事件。
- IVP 联调：消费后库存数量、锁定量均不增加。

正式文档和依赖同步后，按以下顺序独立提交并立即推送：

1. 订单项实际支付字段/分摊契约：由订单模块先落地。

5. 禁止库存回补：请求校验、SQL CHECK、Outbox 断言和 IVP 契约测试。
