# 电子商城项目要求

> 发布方：软件技术专业教研室（教师发布，学生不得修改本目录文件）
> 项目周期：4 周（20 个工作日）

## 一、项目目标

以 4~5 人小组为单位，完成一个 B2C 电子商城系统，覆盖企业软件研发全流程，锻炼以下能力：

1. 需求分析与文档编写能力
2. 系统设计能力（架构、数据库、接口）
3. 前后端编码与协作开发能力
4. 测试与质量保障能力
5. 项目管理与团队协作能力

## 二、功能要求

### 必做功能（占功能分 70%）

**前台（购物端）**

| 模块 | 功能点 |
|------|--------|
| 用户模块 | 注册、登录、退出、个人信息维护、收货地址管理 |
| 商品模块 | 商品列表、分类浏览、关键词搜索、商品详情 |
| 购物车 | 加入购物车、修改数量、删除、结算 |
| 订单模块 | 提交订单、订单列表、订单详情、取消订单 |
| 支付模块 | 模拟支付（无需接入真实支付渠道），支付状态流转 |

**后台（管理端）**

| 模块 | 功能点 |
|------|--------|
| 商品管理 | 商品增删改查、上下架、分类管理 |
| 订单管理 | 订单列表、发货处理、订单状态管理 |
| 用户管理 | 用户列表、禁用/启用 |

### 选做功能（占功能分 10%，至少选 2 项）

- 商品评价与晒图
- 商品收藏、浏览历史
- 站内消息通知
- 商品多规格 SKU（颜色/尺码，库存按 SKU 管理）
- 售后流程（退款/退货申请与后台审核）
- 后台操作日志（谁在什么时间改了什么）

### 挑战模块（占功能分 20%，每组至少完成 1 项）

> 挑战模块的验收方式为：**现场边界演示 / 压测 + 原理抽问**。AI 可以帮你生成代码，但能不能证明它是对的、讲清楚为什么这么做，才是得分点。

| 编号 | 模块 | 要求与验收要点 |
|------|------|----------------|
| C01 | 秒杀与防超卖 | 限时秒杀活动；现场用压测工具模拟并发下单（如 100 并发抢 10 件库存），证明不超卖、不少卖；答辩讲清防超卖方案（事务/锁/队列）及其取舍 |
| C02 | 优惠券规则引擎 | 满减、折扣、优惠券可配置且可叠加校验；优惠金额须**按订单项分摊**（处理除不尽的余数）；部分退款按分摊金额退 |
| C03 | 订单超时自动取消 | 下单 30 分钟未支付自动取消并回补库存；讲清实现机制（定时扫描/延迟任务）；演示"取消瞬间用户恰好支付"的冲突如何处理 |
| C04 | 商品搜索进阶 | 支持分词模糊搜索 + 多条件筛选 + 排序（用搜索引擎或自实现倒排索引均可）；与 LIKE 查询做性能对比并出数据 |
| C05 | 猜你喜欢（推荐） | 基于用户浏览/购买行为的商品推荐（协同过滤或规则均可）；答辩时能对任一用户解释"为什么推荐这个商品" |
| C06 | 实时消息推送 | 用 WebSocket 实现订单状态变更实时通知或在线客服对话；演示断线重连、多标签页场景 |
| C07 | 缓存与性能优化 | 用缓存优化首页/商品详情；解决缓存与数据库的一致性问题（改价后多久生效、为什么）；出压测前后对比报告 |
| C08 | 支付回调幂等与对账 | 模拟支付回调可能重复、乱序到达，保证订单状态正确（幂等处理）；生成每日对账单，能找出"支付成功但订单未更新"的差异数据 |
| C09 | 数据统计看板 | 日/周销售额、分类销量占比、Top10 商品、复购率等多维统计，图表展示；统计 SQL 须手写并能逐句讲解 |
| C10 | 容器化部署与负载均衡 | Docker Compose 一键部署全套系统；Nginx 负载均衡至少 2 个后端实例，说明登录态在多实例下为什么还能用 |

> 挑战模块由某位成员认领后计入其模块包与个人工作量；完成第 2 个及以上挑战模块按加分项计。

## 三、分工要求（模块负责制）

### 3.1 分工原则

1. **不按前后端分工，按业务模块垂直分工**：每人认领模块后，独立完成该模块的数据库表设计、后端接口、前端页面全链路开发。
2. **禁止**出现"一人只写前端 / 一人只写后端"的横向分工，答辩时按模块逐人考核。
3. 组长兼任 **架构员**：第 1 周牵头完成项目脚手架、登录鉴权、统一响应格式、公共组件与数据库初始化，其他成员在此基础上开发各自模块；组长另认领 1 个小模块。

### 3.2 模块划分与难度权重

| 模块包 | 内容 | 难度权重 |
|--------|------|----------|
| 商品包 | 分类、列表、搜索、详情 + 后台商品管理 | 1.0 |
| 订单支付包 | 提交订单、订单管理、模拟支付 + 后台订单管理 | 1.2 |
| 用户购物车包 | 注册登录、个人信息、地址、购物车 + 后台用户管理 | 1.0 |
| 公共基建包（组长） | 脚手架、鉴权、公共组件、集成联调 | 1.1 |
| 测试部署包 | 测试计划/用例/报告、部署 + 至少 1 个选做功能 | 0.9 |

> 个人工作量得分按权重折算；5 人组按上表认领，4 人组将测试部署包职责分摊，须在第 1 周周报中写明最终分工。

### 3.3 协作硬规则

1. **接口文档先行**：模块间调用必须以 `docs/02-设计文档/接口设计.md` 为准，先改文档再改代码。
2. **交叉 Code Review**：每人的分支由相邻模块负责人审查后才能合并，审查记录留痕。
3. **交叉答辩**：答辩时除讲解自己的模块外，每人还会被抽问 1 个其他成员模块的基础问题。

## 四、技术要求

1. 技术栈各组自选，但须满足：**前后端分离**、使用关系型数据库、通过 HTTP API 通信。
2. 技术选型须在第 1 周周报中说明并给出理由。
3. 代码必须托管在本 Git 仓库，遵循 README 中的分支与提交规范。
4. 密码必须加密存储，接口需做基本的参数校验，禁止 SQL 拼接查询。
5. 最终系统需部署到可访问的环境（局域网服务器或校内服务器均可）。

## 六、日报与周报要求

1. **日报**：每人每个工作日一份，当天 18:00 前提交至 `reports/daily/`，命名 `YYYYMMDD-姓名.md`。
2. **周报**：每组每周一份，由组长汇总，周五 18:00 前提交至 `reports/weekly/`，命名 `第N周-周报.md`。
3. 日报周报按模板填写，内容要求真实、具体，禁止空话套话。

## 七、验收与答辩

- 第 4 周最后两天进行现场验收与答辩，详见《验收标准》。
- 评分规则详见《评分标准》。

## 八、纪律要求

1. 严禁抄袭其他组代码与文档，一经发现相关组均按 0 分处理。
2. 允许使用 AI 辅助编程，但须理解所提交的每一行代码。答辩时随机抽问自己模块的实现细节，并交叉抽问其他成员模块的基础问题。
3. 每日考勤与 Git 提交记录挂钩，无提交且无日报视为缺勤。
4. 严禁代写：他人模块的代码不得由本人以外的成员批量提交，Git 记录与分工不符将按情节扣个人分。
